# SANGO 移动端牌桌实现交接

## 1. 文档目的

这份文档用于把当前移动端设计讨论交给新的实现 session。目标是完成真正可用的 mobile 牌桌，而不是逐像素照搬设计原型。

现有 desktop 牌桌已经成型，应尽量复用它的 Web Components、游戏状态、控制器方法和业务规则。移动端可以采用不同的布局 DOM、CSS 或轻量显示组件，因为 desktop 组件的尺寸和交互层级未必适合手机。避免复制 Firebase 读写、选牌、移动卡牌、牌堆整理等业务逻辑。

实现过程中如果某项细节没有足够把握：

1. 优先保持现有 desktop 行为和数据语义。
2. 选择最容易回退的实现，避免为了局部视觉效果重写核心组件。
3. 不阻塞主体布局和主要游戏流程。
4. 在本文末尾的“完成后回看”清单记录该问题，等主体可用后统一调整。

## 3. 已确认的设计目标

### 3.1 一屏完成主要游戏流程

手机进入实际游戏区域后，应能在一个固定游戏 viewport 中看到：

- 五名其他玩家的紧凑概览；
- 公共桌面及最近弃牌；
- 本地玩家的武将、体力、状态和装备摘要；
- 当前卡牌区域；
- 持久位于卡牌区域下方的 bottom bar。

不要求彻底禁用页面纵向滚动。移动浏览器需要少量纵向滚动来触发地址栏自动隐藏。当前原型的思路是让顶部栏和少量非关键内容成为这段可滚动高度，真正的 `.game-viewport` 使用约 `100lvh` 并在内部稳定排版。

不要把 bottom bar 做成覆盖手牌的 fixed overlay。它应当是游戏 viewport 布局中的固定一行，始终位于手牌区下方。浏览器地址栏显示或隐藏、`visualViewport` 高度变化时，手牌区和工具栏不能互相覆盖或发生明显跳动。

### 3.2 以 390 CSS px 为主要设计基准

讨论中选择 390px 作为近几年常见 iPhone 竖屏的主要设计宽度。它是设计基准，不应成为只支持 390px 的硬限制。

- 先确保 390px 宽度下完整显示。
- 同时检查较窄手机和 Android Chrome 的实际 CSS viewport。
- 禁止横向页面滚动。
- 玩家卡宽度应保持稳定，不随 viewport 拉伸而变宽。
- 当前原型最终使用约 89px 的玩家卡宽度；曾测试 88、89、90px，90px 在真机上出现最右侧轻微 cut-off。实现时可根据真实容器、边框盒模型和 gap 重新计算，89px 只是可靠起点。
- 最左玩家卡与公共桌面的左边界对齐；最右玩家卡与下排右侧玩家卡对齐；中间 gap 应由可用空间自动分配。

### 3.3 信息优先，整张玩家卡作为交互入口

移动端的对手卡首先是一张只读信息摘要。手牌、区1、区2、装备和状态不需要分别做成带边框的小按钮。用户点击整张 player card 后，再进入二级面板与这些区域交互。

期望布局为顶部四名对手，另一个对手位于公共桌面右侧。这样五名对手都可以同时留在视野中。玩家卡之间可使用非常淡的分割线帮助阅读，但不要恢复为大量独立方框。

对手卡至少显示：

- 玩家名和身份；
- 已亮武将图；
- 体力；
- 最多四件装备的文字摘要；
- 手牌、区1、区2的牌数；
- 翻、链、乐、兵、电等状态。

座次 `2、3、4、5、6` 不需要单独显示。名字下方可以保留克制的分割线。

### 3.4 武将显示

- 点击武将头像可打开武将详情，查看名称、性别等信息。
- 未亮武将不显示名字；亮将后才显示名字。
- 本地玩家始终需要看见自己的武将名称，并有“亮将”入口。
- 双将和长名字必须可用。原型用 `界颜良文丑`（五个字）与 `SP黄月英` 做压力测试。
- 长名字可以缩小字号、减少字距或使用竖排，但不能挤压其他关键信息或溢出卡片。
- 为控制总高度，对手武将图可以比早期方案略矮；优先保证头像仍可辨认。

### 3.5 装备摘要和装备详情

玩家卡上的装备只显示装备名称，不显示 suit 和 number，也不把每件装备做成独立按钮或边框卡。整张玩家卡点击后，在二级面板查看完整装备牌和执行操作。

摘要最多两行，超出时截断，不能继续撑高玩家卡。实际压力测试组合为：

`丈八蛇矛、八卦盾、爪黄飞电、赤兔`

装备之间不要依赖字体字符 `·`、`｜` 或类似分隔符。真机字体可能给字符加入异常字距，并且换行时分隔符容易落在行首或行末。建议用 CSS `border`、伪元素或 grid 分栏绘制分隔。还应检查 0、1、2、3、4 件装备的样式；0 件时不要显示“空位”。

### 3.6 区域牌数

对手卡需要同时显示手牌、区1、区2的数量，并支持两位数。讨论过 icon 和文字两种方式：icon 节省字面空间，但小尺寸下辨识度不稳定；文字更直观。

最终实现可根据真机可读性决定横向或上下结构：

- 目标是三组信息在一行内完成，不增加玩家卡高度；
- 每组内部可以是“区名在上、count 在下”，也可以紧凑并排；
- 两位数不能挤压相邻区域；
- 不使用三块带边框的二级区域。

当前 Plan E 原型保留的是三个等宽格，每格内紧凑显示文字和 count。这里属于可调视觉细节。

### 3.7 状态与判定摘要

状态用短文字显示：`翻、链、乐、兵、电`。不要给判定状态再创建三个二级区域，也不要显示 `1、2、3` 序号。判定牌在数据中的从左到右顺序本身就是结算顺序。

- `乐`、`兵`、`电` 可参考 `docs/SANGO_OPPONENT_PLAYER_CARD_COMPACT_V1.html` 的概念，但当前信息摘要使用纯文字，不要背景 tile 和边框。
- 颜色应低饱和并符合现有墨绿、旧金和纸色主题。
- `乐` 使用克制的赭红文字，不使用醒目的朱红底。
- `兵` 使用接近墨色但仍能从深绿背景辨认的浅墨灰。
- `电` 可用低饱和金黄或暖色。
- `翻` 与 `链` 也要和其他状态有足够区别。
- 需要用 `翻、链、乐、兵、电` 全部同时存在做压力测试。

具体色值允许实现 agent 根据生产 CSS 调整。验收重点是能辨认、整体协调、无彩色徽章堆叠感。

### 3.8 本地玩家区域

本地玩家区域应比 desktop 小，并比早期 mobile 原型更紧凑。武将图仍需明显大于对手卡里的单个小头像。

装备摘要放在状态下方、武将右侧的剩余空间中，使用可换行文字；点击“装备”区域进入完整卡牌区域。判定区也必须能进入并选择卡牌。手牌、区1、区2、装备、判定的区域视图尽量共享同一种卡片浏览和选牌模式。

判定摘要只显示按顺序排列的 `乐、兵、电` 等状态。进入判定区后显示实际判定牌，并按从左到右的顺序操作。

### 3.9 手牌区域

- 手牌横向滚动，页面本身不横向滚动。
- 卡牌尺寸应比 desktop 小，以控制纵向高度。
- 当前原型的参考值为手牌区域约 98px，牌面约 40×58px；这是起点而非不可变规格。
- 选择牌后要有明确但轻量的选中反馈，不能因为向上浮动而被容器裁切。
- 切换手牌、区1、区2、装备、判定时清除或正确迁移 selection，避免工具栏显示针对旧区域的操作。

## 4. Bottom bar 的最终交互方向

Bottom bar 是持久布局行，但其内容根据 selection 状态切换。

### 4.1 没有选中卡牌

显示公共桌面的高频入口：

- 摸牌；
- 展示／判定；
- 观看或展开牌堆；
- 当牌堆为空时，可以把对应入口替换为洗牌。

“摸牌”点击后可以打开 1–4 张选择，不需要把四个数量长期占在底栏。

### 4.2 已选中卡牌

整行切换为针对 selection 的操作，候选包括：

- 取消选择；
- 收入手牌；
- 出牌；
- 移动；
- 亮牌；
- 暗置；
- 弃置。

按钮应根据选中来源和卡牌状态显示或隐藏，而不是让所有动作一直出现。例如：

- 自己手牌可出牌、移动、亮牌/暗置、弃置；
- 自己其他区域根据现有 controller 规则隐藏不可用动作；
- 弃牌堆选择通常只允许收入手牌和取消；
- 已亮牌只需要暗置入口，未亮牌只需要亮牌入口；混合 selection 的表现可沿用 desktop 的统一切换语义，或拆成两个动作，只要不会产生歧义。

两种 bottom bar 状态必须保持相同外部高度，切换时不能导致手牌区、local player 区或整个 viewport 位移。按钮数量较多时，优先动态隐藏不适用动作；确实放不下时再考虑底栏内部横滑或“更多”，不要增加第二行。

当前 desktop 已有 `sgTable.getCardMenu()` 和 `syncSelectionMenus()` 管理 selection 操作。mobile 应尽量复用同一份 selection 和 controller 方法，只改变呈现方式。

## 5. 公共桌面功能

当前 desktop 的 `publicTablePanel.js` 是功能基准，mobile 需要覆盖：

- 显示牌堆剩余数量；
- 从牌顶摸 1–4 张；
- 展示／判定牌顶第一张，并让该牌进入弃牌堆；
- 牌堆为空时将弃牌洗回牌堆；
- 显示最近 6 张弃牌，顺序为最新到较早；
- 显示弃牌来源，例如打出、弃置、展示／判定；
- 查看全部弃牌；
- 从弃牌堆收入手牌；
- 展开牌堆后私下观看、上下排序、放牌底、加入确认摸牌列；
- 调整牌堆在确认时一次提交，取消不修改真实数据；
- 私下观看只记录必要的行动日志，不泄露牌面。

公共桌面主体应主要展示牌堆数量和弃牌信息。高频命令放到未选牌状态的 bottom bar，避免公共桌面堆满按钮。牌堆整理、全部弃牌等复杂内容进入 modal、dialog、popover 或 bottom sheet。

弃牌卡可以使用更小的 tile。点击 tile 后再显示完整牌面和可用操作。

行动日志放在公共桌面下方的一行摘要，点击后展开完整日志。它不应嵌进弃牌布局，也不能覆盖右侧的第五名玩家卡。

## 6. 组件复用建议

推荐复用层级如下：

1. **必须优先复用业务层**：`gameController` 的选牌、摸牌、出牌、弃置、亮暗、移动、牌堆整理和 Firebase 路径语义。
2. **尽量复用卡牌与区域组件**：优先通过 CSS parts、host class、slot 或小型 wrapper 让 `sg-card`、区域浏览、player 数据订阅适应 mobile。
3. **允许使用不同的牌桌布局壳**：desktop 的绝对定位、侧栏工具条和大尺寸 player DOM 如果使 mobile 难以稳定布局，可以给 `sg-table` 增加 mobile renderer/layout，或在同一组件内部按模式输出不同的布局容器。
4. **不要维护两套独立业务状态**：如果使用两种 DOM 结构，两者仍应订阅同一个 controller/state，并共享 action handlers。

响应模式可由 CSS media query 和一个清晰的 mobile layout class 共同决定。只靠复制整棵 desktop DOM 再用 `display:none` 隐藏，容易产生重复订阅、重复 id、焦点和弹窗问题。只靠 CSS 强行压缩 desktop 绝对定位，也可能继续出现真机 overlay。实现 agent 可以选择折中方案，但需要让 viewport 切换后的生命周期和订阅保持单一、可清理。

不要为了复用而强行保留不适合触屏的 hover、窄侧边工具条或 desktop 固定高度。复用的重点是数据、行为、卡牌渲染和无障碍语义。

## 7. 已遇到的真机问题

以下问题来自 Android Chrome 真机截图和迭代：

- desktop 或模拟器看起来合适，手机仍会在最右玩家卡发生轻微 cut-off；
- 地址栏自动隐藏会改变可视高度，曾导致手牌区域增高并推动 bottom toolbar；
- fixed/sticky overlay 会遮住手牌或右侧玩家卡；
- 使用字体分隔符时，手机字体产生异常的大间距；
- 装备换行时字符分隔符会留在错误的行首或行末；
- 装备第二行 line-height 曾与第一行不一致；
- 四件长装备可能让卡片高度失控；
- 小 icon 在真实屏幕上不一定比“手、区1、区2”更清楚；
- 鲜艳的状态底色与游戏现有配色不协调；
- topbar、bottom bar 和手牌区原本过高，浏览器地址栏出现时全局被裁切。

实现时应优先在真实移动 viewport 验证盒模型、safe-area、浏览器 chrome 显隐以及字体 fallback，不能只依赖 desktop 窗口缩放。

## 8. 建议实现顺序

1. 建立 mobile layout 模式和稳定的 viewport 高度模型。
2. 放入五名对手、本地玩家、公共桌面、手牌和空的 bottom bar，先消除横向溢出与遮挡。
3. 接入现有 player/card 数据，只做只读摘要。
4. 接入区域切换和统一 selection。
5. 接入 contextual bottom bar，并复用 controller actions。
6. 接入公共牌堆、弃牌、牌堆整理和行动日志的二级面板。
7. 接入玩家卡点击后的手牌、区1、区2、装备、判定和武将详情。
8. 最后进行真机尺寸、颜色、字体、分隔线和动效调整。

主体阶段不要因一个 icon、单个色值、1px gap 或某种弹窗动画停下来。先保证所有关键状态与操作都能到达，并且不会重叠或丢失。

## 9. 验收场景

至少检查以下场景：

- 390px 宽度下顶部四张玩家卡完整显示，最右边不裁切；
- 右侧第五名玩家卡不被公共桌面或行动日志覆盖；
- 360px 左右窄屏没有页面横向 scrollbar；
- 地址栏从显示到隐藏时，bottom bar 仍在手牌区下方且没有明显跳动；
- 对手手牌为 11 或更大时 count 正常；
- 玩家有 0、1、2、3、4 件装备时摘要都合理；
- 四件压力测试装备最多占两行；
- `界颜良文丑`、`SP黄月英` 不溢出；
- 未亮武将没有名称，亮将后名称出现；本地玩家可看到自己的名称并可亮将；
- `翻、链、乐、兵、电` 同时出现仍清楚；
- 判定牌按从左到右顺序显示，没有额外的 1/2/3 区块；
- 未选牌 bottom bar 显示牌堆操作；选牌后同一位置切换为卡牌操作；取消选择后恢复；
- 从不同区域选择牌时，只出现合法动作；
- 手牌、区1、区2、装备、判定都可打开并完成适用交互；
- 最近弃牌、全部弃牌、收入手牌、展示／判定、牌堆整理和空牌堆洗牌均可到达；
- modal/bottom sheet 打开后不造成背景布局移位，关闭后 selection 和滚动位置合理。

## 10. 完成后回看

以下内容允许在主体完成后再决定：

- 对手区域牌数最终使用文字还是 icon；
- 区名与 count 是上下排列还是紧凑并排；
- 玩家卡最终宽度是 88、89、90px，或由 CSS 公式得到等效宽度；
- 状态文字的最终色值；
- 复杂动作使用 dialog、popover 还是 bottom sheet；
- bottom bar 在极窄屏上采用隐藏动作、“更多”还是内部横滑；
- desktop 与 mobile 是否共享同一套 player 摘要 DOM，或只共享数据 adapter；
- topbar 在游戏模式中保留哪些房间信息；
- 是否使用 `visualViewport` 辅助处理特定浏览器问题。只有 CSS viewport 单位无法解决真实问题时再引入 JS 测量。

记录这些问题即可，不需要在主体实现中提前锁死。最终判断应基于 production 组件、真实数据和手机截图，而不是静态原型单独决定。
