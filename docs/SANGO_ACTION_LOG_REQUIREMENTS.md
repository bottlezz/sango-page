# 行动日志需求与实现

> 当前文档描述现有用户需求及临时实现。日志架构、数据库流量、subscription 驱动方案与迁移事项，统一记录在 [`SANGO_ACTION_LOG_REDESIGN_HANDOFF.md`](./SANGO_ACTION_LOG_REDESIGN_HANDOFF.md)。后续 session 应先阅读该文档；当前实现不视为最终架构。

设计参考：`SANGO_BOARD_LAYOUT_PLANS_V2_BORDERLESS.html` 方案 D 的右下角「行动日志」。

## 日志记录范围

| 操作 | 记录内容 |
| --- | --- |
| 拖拽、摸牌、出牌、弃牌、跨玩家移动 | 操作者、来源区域及移出数量、目标区域及移入数量 |
| 手牌、装备、判定、区1、区2之间移动 | 同上，包含目标玩家座次 |
| 判定牌入区 | 所选效果：乐不思蜀、兵粮寸断、闪电 |
| 区域内排序 | 区域名称及“调整牌序”；判定区额外显示效果顺序 |
| 卡牌、武将亮置或暗置 | 区域、亮出／暗置、数量 |
| 翻面、连环 | 目标玩家、开启／解除 |
| 当前体力、体力上限变化 | 目标玩家、完整前后数值，例如 `p1 体力：4/5 → 3/5` |
| 身份分配 | 目标玩家“身份已更新”，不记录身份值 |
| 发将、选将确认、武将移位 | 各武将区域进出数量，确认／解除选将锁定 |
| 发牌 | 各玩家手牌增加数量及牌堆减少数量 |
| 洗牌、清台 | 涉及区域的牌数变化；洗牌标注操作名称 |

所有实际游戏卡牌区域都纳入记录，包括历史数据中的牌堆底部、主将、副将、选将区及公共武将区域。

## 记录规则

- 日志由发起操作的客户端在数据库事务内生成，与状态变更同时提交。观看端只读取，不通过监听变化生成日志，避免多人重复记录。
- 每次数据库操作提交对应一条日志，可包含多项区域或状态变化。多牌拖拽、多选后「摸／弃／出」、区域弹窗「拿取所选／弃置所选」均批量提交，一次操作一条日志；失败时整批不移动。目标区域中已有的所选牌不重复移动，空选择不写日志。
- 取消、失败、重复设置同一值、点击选牌、打开菜单、滚动、拖动预览不记录。
- 新牌进入判定区默认追加；拖拽重排后日志记录新的判定顺序。
- 进入公共区自动清除亮置、移出判定区清除判定效果，作为该次移动的结果，不额外产生一条用户操作。
- 不补写功能上线之前的历史。刷新或重新加入房间读取既有日志。清台保留日志。
- 房间创建、入座改名，以及绕过游戏直接修改数据库不在此客户端日志范围内。

## 隐藏信息

公共日志不保存卡牌 ID、花色、点数、牌名或武将姓名；明牌也统一按区域和数量记录。这样历史日志不会暴露随后暗置的卡牌或未亮武将。判定效果属于公开信息，可以记录。

## 显示与保存

- 桌面位置及尺寸采用方案 D：右下角、330×246，时间列＋操作文字，可折叠；窄屏排列在桌面内容下方。
- 使用服务器时间；显示时分，悬停显示完整日期时间。操作者包括座次和操作时用户名。
- 按记录键的时间顺序显示；在底部时自动跟随，向上查看历史时不抢走滚动位置。
- 路径：`game/{gameId}/actionLogs/{pushKey}`。
- 字段：`actor`、`timestamp`、`action`（可空）、`changes`（描述列表）。
- 保留最近 500 次提交，超出时随下一次操作删除最旧记录，控制房间事务与界面负载。不是永久审计档案。
- 数据写入统一通过 `gameController.commitRoom`／`writePatch`／`setValue`。新增游戏状态操作必须接入这一通道，并扩展 `describeChanges` 的字段规则。

## 验收

1. 牌堆到手牌、装备到公共区、跨玩家区域移动都有来源／目标及数量。
2. 判定选择效果后产生记录，取消不产生记录；排序只记录顺序变化。
3. 翻面、连环开关与体力及上限的前后数值正确。
4. 刷新保留记录，多人接收同一条记录；事务重试不重复追加。
5. 日志不包含任何隐藏牌的身份信息；同值写入不产生记录。
6. 桌面日志可折叠、可滚动，阅读旧记录时不强制跳到底部。
